# 定位收发和后台模拟验收

用户批准于 2026-11-07。工作区从 main 建立，再快进到首页 af989be。参考源为桌面定位项目 6dda1276c3115877fcb0cc80313d71ff6cbd0092。

1. 单独创建 API 36 AVD，选定明确的模拟器控制端口；仅在宿主回环地址提供测试服务，隔离数据库和两个虚拟家庭。
2. 复用安卓定位服务和队列、服务端幂等接收及家庭鉴权。区分采集、入库与页面显示时间，停止共享后停止传输及执行请求。
3. 家人端登录和绑定后每 30 秒前台刷新；位置超过 10 分钟提示过期。立即定位只接受匹配请求的新点。
4. 先测完整 30 分钟锁屏移动，联网时采集间隔达标率（≤90秒）至少 90%，入库延迟达标率（≤60秒）至少 95%，包含起止边界的无新点时长 ≤3 分钟。联网静置最长间隔 ≤10 分钟。单测 Doze、断网 15 分钟与 2 分钟内开始补传、进程回收、重启、强停和明确恢复。
5. 短测通过后按真实时钟持续 24 小时。标注所有测试中断，隔离模拟点与可信位置。保存模拟器及小程序证据，CI 与设备实测分别交付。


## 验收测量的补充说明

长测实际发现两个环境问题。Windows ADB 连接曾报 10055，此窗口中断并重测。允许对已确认的宿主连接失败进行两次有上限重试，设备端错误仍使验收失败。

AVD 与 PostgreSQL 时钟的实测差约 1.1 秒，直接相减得到负延迟。原失败统计保存在证据目录。保留两端原始时间并额外用系统输入的不同速度匹配正式回调产生的点，以同一个宿主单调时钟记录 GPS 输入之前和入库确认之后。该区间是采集至入库耗时的上限，95% / 60 秒指标照常适用，未匹配点按未达标计。设备、接口与数据库格式沿用原实现。

Critic Loop 的问题是两台机器的墙上时钟不能直接证明经过时间，已由实际负值及只读钟差查询复现。继续直接相减会留下不可解释的负值，45/100。调整系统时间可能改变采集排序且需要持续同步，55/100。采用同一个观察器时钟、匹配唯一速度来源并保留原始差值，需要增加采证文件和回归测试，能给出保守上限，90/100，采纳。完整 30 分钟复测已证明 60 个点全部匹配。

来源为只读数据库、系统 GPS 控制台和独立入库查询。真实定位和强制休眠按批准方案执行。vivo 真机和微信发布继续作为后续事项。
